# Кузница Кода — Локальный оркестратор ИИ-разработки

Серверное приложение на **Node.js 22 + TypeScript (strict) + Express + WebSocket + SQLite (WAL)** с веб-интерфейсом на React, Vite и Tailwind CSS. Конвейер детерминированно управляет тремя агентами (Архитектор, Кодер, Ревьюер) по стадиям `PLAN → CODE → INSTALL → BUILD/TEST → REVIEW → FIX`, изолирует сборку и тесты в контейнерах (или локальном fallback-режиме), контролирует бюджет в рублях и сохраняет всё состояние в SQLite.

## 1. Системные требования и подготовка ОС

### Минимальные ресурсы
- **ОЗУ**: от 2 ГБ (для стеков `ts-web`, `node-api`, `python`); **от 3 ГБ свободной ОЗУ** для стека `kotlin` (Gradle JVM; при меньшем объёме UI автоматически блокирует выбор Kotlin).
- **Диск**: от 5–10 ГБ свободного места под Docker-образы, кэши зависимостей (`npm`, `pip`, `gradle`) и рабочие проекты.
- **Сеть**: доступ к вашему OpenAI-совместимому LLM-шлюзу (с оплатой в ₽).

### Подготовка Windows (WSL2 + Docker Desktop)
Для стабильной работы Docker, сборки Node/Python и особенно **Kotlin/Gradle JVM** настройте лимиты WSL2:

1. Откройте или создайте файл `C:\Users\<ИмяПользователя>\.wslconfig`:
   ```ini
   [wsl2]
   memory=6GB
   processors=4
   swap=2GB
   localhostForwarding=true
   ```
2. Перезапустите WSL2 из PowerShell (от имени обычного пользователя или администратора):
   ```powershell
   wsl --shutdown
   ```
3. В настройках **Docker Desktop** убедитесь, что включён **Use the WSL 2 based engine** (и при необходимости интеграция с нужным дистрибутивом WSL2).

### Подготовка Linux / macOS
- **Для запуска в Docker (рекомендуемый режим)**: установите **Docker Engine** и плагин **Docker Compose v2** (`docker compose version`).
- **Для запуска без Docker (`RUNNER_MODE=process`)** на хосте должны быть установлены:
  - **Node.js 22+** и `npm`
  - **Git** (`git --version`)
  - Инструменты сборки нативных модулей C/C++ для `better-sqlite3` (`build-essential` + `python3` на Linux, Xcode Command Line Tools на macOS, Desktop development with C++ на Windows — если отсутствуют готовые бинарники)
  - Для Python-проектов: **Python 3.11+** с модулем `venv`
  - Для Kotlin-проектов: **JDK 17+** и **Gradle** (или `gradlew`/`gradlew.bat` в проекте)

## 3. Шаг 2. Настройка переменных окружения (`.env`)

1. Скопируйте шаблон конфигурации:
   ```bash
   cp .env.example .env
   ```
   На Windows (PowerShell):
   ```powershell
   Copy-Item .env.example .env
   ```

2. Сгенерируйте криптографические ключи для `JWT_SECRET` и `MASTER_KEY` (две разные случайные строки не короче 32 символов):
   ```bash
   # Linux / macOS / Git Bash / WSL
   openssl rand -hex 32
   openssl rand -hex 32
   ```
   Либо с помощью Node.js (работает на любой ОС):
   ```bash
   node -e "console.log(require('crypto').randomBytes(32).toString('hex'))"
   ```
   > **Важно:** `MASTER_KEY` используется для шифрования `llm_api_key` алгоритмом AES-256-GCM перед сохранением в SQLite. Если не задать `MASTER_KEY` в `.env`, сервер создаст ключ локально в папке `data/`, но при переносе базы на другой сервер без сохранения этого ключа расшифровать старый API-ключ не получится.

3. (Опционально, рекомендуется для продакшена) Сформируйте bcrypt-хэш пароля администратора для `ADMIN_PASSWORD_HASH`:
   ```bash
   node -e "import('bcryptjs').then(async ({default: b}) => console.log(await b.hash('ВашНадёжныйПароль', 10)))"
   ```
   Если `ADMIN_PASSWORD_HASH` и `ADMIN_PASSWORD` оставить пустыми, при первом открытии браузера приложение предложит задать пароль администратора через веб-интерфейс и сохранит его хэш в `data/orchestrator.db`.

4. Заполните `.env` согласно таблице параметров:

| Переменная | Назначение | Значение по умолчанию / пример |
|---|---|---|
| `APP_MODE` | Режим развёртывания (`local` или `public`) | `local` |
| `PORT` | Порт HTTP/WebSocket-сервера внутри Node/контейнера | `3000` |
| `APP_URL` | Внешний URL приложения | `http://localhost:3000` (или `https://example.com`) |
| `ADMIN_USERNAME` | Логин администратора | `admin` |
| `ADMIN_PASSWORD` | Пароль администратора в открытом виде (удобно только для локальной отладки) | *(пусто)* |
| `ADMIN_PASSWORD_HASH` | Bcrypt-хэш пароля администратора (имеет приоритет над `ADMIN_PASSWORD` и БД) | `$2b$10$...` |
| `JWT_SECRET` | Секрет для подписи JWT-токенов сессии | `64-символьная hex-строка` |
| `MASTER_KEY` | Ключ AES-256-GCM для шифрования секретов в SQLite | `64-символьная hex-строка` |
| `LLM_BASE_URL` | Базовый URL OpenAI-совместимого шлюза (обычно заканчивается на `/v1`) | `https://api.example.ru/v1` |
| `LLM_API_KEY` | API-ключ шлюза (можно не писать в `.env`, а ввести позже в «Настройки») | `sk-...` |
| `ARCHITECT_MODEL` | Идентификатор модели Архитектора (DeepSeek, read-only) | задаётся из списка вашего шлюза |
| `CODER_MODEL` | Идентификатор модели Кодера (Gemini Pro, единственный пишет файлы) | задаётся из списка вашего шлюза |
| `REVIEWER_MODEL` | Идентификатор модели Ревьюера (Qwen, read-only) | задаётся из списка вашего шлюза |
| `DEFAULT_PROJECT_BUDGET_RUB` | Бюджет по умолчанию на один проект (₽) | `50` |
| `DAILY_BUDGET_RUB` | Суточный общий лимит расходов (₽) | `300` |
| `SKIP_REVIEW` | Пропуск стадии `REVIEW` по умолчанию для ускорения/экономии (`true`/`false`) | `false` |
| `ALLOW_CODER_FALLBACK` | Разрешить переключение Кодера на модель Архитектора при сбое (`true`/`false`) | `false` |
| `RUNNER_MODE` | Режим раннера: `docker` (контейнеры) или `process` (локальные процессы) | `process` (в Compose переопределяется на `docker`) |
| `RUNNER_INSTALL_URL` | Адрес сервиса установки зависимостей в Docker-сети | `http://runner-install:4001` |
| `RUNNER_EXEC_URL` | Адрес изолированного сервиса сборки и тестов в Docker-сети | `http://runner-exec:4002` |
| `DATA_DIR` | Каталог с SQLite-базой `orchestrator.db` | `./data` |
| `WORK_DIR` | Каталог с рабочими Git-репозиториями проектов (`work/<project_id>`) | `./work` |
| `TEMPLATES_DIR` | Каталог со стартовыми шаблонами стеков | `./templates` |
| `PUBLIC_DOMAIN` | Домен для автоматического выпуска TLS-сертификата в `Caddyfile` | `localhost` (для VPS: `app.example.com`) |

## 4. Шаг 3. Запуск приложения (3 способа)

### Вариант А: Docker Compose — профиль `local` (рекомендуемый для домашнего ПК)

В этом режиме поднимаются 3 контейнера:
- `app` — основной сервер и веб-интерфейс, привязанный строго к `127.0.0.1:8080` (не виден извне сети);
- `runner-install` — контейнер с доступом в интернет только для установки зависимостей (`npm`, `pip`, `gradle`);
- `runner-exec` — изолированный контейнер для сборки и запуска тестов **без доступа в интернет** (`internal: true`), без `docker.sock`, с `cap_drop: ALL`, `no-new-privileges: true`, `mem_limit: 2g`, `pids_limit: 256` и общими volume-кэшами (`npm-cache`, `pip-cache`, `gradle-cache`).

**Пошаговый запуск:**
1. Убедитесь, что `.env` создан (достаточно заполнить `JWT_SECRET`, `MASTER_KEY` и при желании параметры LLM).
2. Соберите образы и запустите сервисы в фоне:
   ```bash
   docker compose --profile local up -d --build
   ```
   > Первый билд `runner/Dockerfile` занимает несколько минут, так как предварительно устанавливает Python/ruff/pytest, Node.js, JDK, Gradle и прогревает кэш шаблона Kotlin. Последующие запуски стартуют за секунды.
3. Проверьте статус контейнеров и healthcheck:
   ```bash
   docker compose --profile local ps
   curl -s http://127.0.0.1:8080/api/health
   ```
   Ожидаемый ответ содержит `"ok":true` и `"runnerMode":"docker"`.
4. Откройте интерфейс в браузере: **`http://127.0.0.1:8080`**.

Полезные команды управления:
```bash
# Просмотр логов
docker compose --profile local logs -f app

# Остановка без удаления данных и кэшей
docker compose --profile local down
```

### Вариант Б: Docker Compose — профиль `public` (+ Caddy Auto-TLS для VPS)

Используйте этот профиль при развёртывании на выделенном сервере с собственным доменом:

1. В панели управления DNS вашего домена создайте A-запись, указывающую на публичный IPv4-адрес сервера.
2. Откройте на сервере входящие TCP-порты `80` и `443`.
3. В файле `.env` задайте:
   ```dotenv
   APP_MODE=public
   PUBLIC_DOMAIN=forge.example.com
   APP_URL=https://forge.example.com
   ADMIN_USERNAME=admin
   ADMIN_PASSWORD_HASH=$2b$10$...   # обязательно для публичного сервера!
   JWT_SECRET=<случайные_64_hex_символа>
   MASTER_KEY=<случайные_64_hex_символа>
   ```
4. Запустите профиль `public`:
   ```bash
   docker compose --profile public up -d --build
   ```
5. `Caddy` автоматически получит TLS-сертификат Let's Encrypt и начнёт проксировать HTTPS и WebSocket на `app:3000`.
6. Откройте в браузере **`https://forge.example.com`**.

### Вариант В: Локальный запуск без Docker (`RUNNER_MODE=process`)

Если Docker не установлен или вы хотите запускать сборки напрямую на хосте (Linux, macOS или Windows):

1. В `.env` убедитесь, что задано:
   ```dotenv
   RUNNER_MODE=process
   PORT=3000
   APP_URL=http://localhost:3000
   ```
2. Установите зависимости:
   ```bash
   npm install
   ```
3. **Запуск в режиме разработки** (Express + Vite middleware):
   - Linux / macOS:
     ```bash
     RUNNER_MODE=process npm run dev
     ```
   - Windows PowerShell:
     ```powershell
     $env:RUNNER_MODE="process"; npm run dev
     ```
4. **Запуск в production-режиме** (собранный фронтенд из `dist/` раздаётся самим Express):
   - Linux / macOS:
     ```bash
     npm run build
     NODE_ENV=production RUNNER_MODE=process npx tsx server.ts
     ```
   - Windows PowerShell:
     ```powershell
     npm run build
     $env:NODE_ENV="production"; $env:RUNNER_MODE="process"; npx tsx server.ts
     ```
5. Откройте **`http://localhost:3000`**.
   > При работе в режиме `RUNNER_MODE=process` в верхней системной панели отображается предупреждение **«Сниженная изоляция (без Docker-песочницы)»** — команды сборки/тестов запускаются как дочерние процессы на вашей ОС с контролем таймаутов и завершением дерева процессов.

## 5. Шаг 4. Первичная настройка в веб-интерфейсе

После открытия приложения в браузере выполните следующие действия:

1. **Авторизация администратора**
   - Если `ADMIN_PASSWORD` / `ADMIN_PASSWORD_HASH` не были заданы в `.env`, отобразится форма **первичной установки пароля** — задайте логин и надёжный пароль (минимум 8 символов).
   - Если учётные данные уже указаны в `.env`, просто войдите с ними.

2. **Подключение LLM-шлюза и выбор моделей**
   - Перейдите в боковом меню в раздел **«Настройки»**.
   - Укажите **`LLM_BASE_URL`** вашего OpenAI-совместимого провайдера (например, `https://api.example.ru/v1`).
   - Введите **`LLM_API_KEY`** и нажмите **«Сохранить настройки»** — ключ зашифруется через AES-256-GCM с помощью `MASTER_KEY` и сохранится в SQLite (после сохранения в интерфейсе отображается только замаскированный префикс).
   - Нажмите **«Обновить список моделей»** (`GET /api/llm/models`), чтобы подтянуть доступные модели напрямую со шлюза.
   - Назначьте модели для трёх ролей:
     - **Архитектор (`ARCHITECT_MODEL`)** — составляет план и проводит отладку (только чтение).
     - **Кодер (`CODER_MODEL`)** — единственный агент, который создаёт/изменяет/удаляет файлы через `FilePatch JSON`.
     - **Ревьюер (`REVIEWER_MODEL`)** — проверяет `git diff` (только чтение).
   - Нажмите кнопку **«Проверить»** (`POST /api/llm/ping`) и дождитесь подтверждения успешного ответа и замера задержки (мс).

3. **Бюджет, тарифы и системные промпты**
   - В этом же разделе при необходимости скорректируйте:
     - дневной лимит (`DAILY_BUDGET_RUB`) и бюджет проекта по умолчанию (`DEFAULT_PROJECT_BUDGET_RUB`);
     - стоимость входных и выходных токенов (₽ за 1 млн токенов) для точного расчёта расходов каждого агента;
     - системные промпты Архитектора, Кодера и Ревьюера;
     - лимит контекстного окна (`context_window_tokens`) и флаг пропуска ревью (`skip_review`).

## 6. Шаг 5. Работа с проектами, логами и бюджетом

1. Перейдите в **«Новый проект»**, введите название, выберите технологический стек (`ts-web`, `node-api`, `python` или `kotlin`), опишите техническое задание, задайте бюджет в рублях и нажмите **«Создать и запустить»**.
   - В очереди одновременно выполняется **один проект** — остальные ждут со статусом `В очереди`.
   - При перезапуске ПК или сервера прерванный проект автоматически переводится из `Выполняется` в `Пауза`; для продолжения со стадии остановки нажмите **«Продолжить»**.
2. В **«Рабочей зоне»** проекта доступны:
   - **Дерево файлов и просмотр кода / `git diff`** с подсветкой синтаксиса (`PrismJS`).
   - **Лента агентов** в реальном времени (WebSocket) с детализацией JSON-ответов и стоимостью каждого шага.
   - **Линейный график расхода бюджета (`BudgetChart`)** на базе Recharts — отображает накопительный расход (₽), расход за каждую итерацию и лимит бюджета по мере поступления WebSocket-событий `project:event`.
   - **Вкладки диагностики** (`Build`, `Tests`, `Review`, `Ошибки стека`, `План`) и кнопка **«Скачать логи»**, которая собирает логи установки, сборки и тестов из `projectDetail.commandRuns` для текущей (или выбранной из выпадающего списка) итерации в `.txt`-файл.
   - **Управление**: «Отмена» (прерывает генерацию и дочерние процессы), «Доработать» (вносит правки по новой инструкции с повторным прогоном тестов и ревью) и «ZIP» (скачивает готовый проект архивом).

## 7. Шаг 6. Безопасный удалённый доступ (туннели)

В профиле `local` сервер слушает только `127.0.0.1:8080`. Чтобы безопасно подключаться к нему с ноутбука или телефона без публикации портов в интернет:

- **Через SSH-туннель:**
  ```bash
  ssh -L 8080:127.0.0.1:8080 user@your-pc-or-server
  ```
  После подключения открывайте локально в браузере `http://127.0.0.1:8080`.

- **Через Cloudflare Tunnel (`cloudflared`):**
  ```bash
  cloudflared tunnel --url http://127.0.0.1:8080
  ```

## 8. Шаг 7. Резервное копирование и перенос на VPS

### Что нужно бэкапить
- `./data/orchestrator.db` (и рядом лежащие `-wal` / `-shm`) — проекты, события, логи ошибок стеков, зашифрованные настройки и история расходов.
- `./work/` — рабочие Git-репозитории сгенерированных проектов.

### Безопасное создание резервной копии
```bash
# Вариант 1: горячий снимок SQLite без остановки сервера
sqlite3 ./data/orchestrator.db ".backup './backup-orchestrator-$(date +%F).db'"

# Вариант 2: полная архивация data/ и work/ с кратковременной остановкой app
docker compose --profile local stop app
tar -czf backup-$(date +%F).tar.gz data/ work/
docker compose --profile local start app
```

### Переезд на VPS без изменения кода
1. Скопируйте проект, каталоги `data/` и `work/` на новый сервер.
2. Скопируйте `.env` (обязательно сохраните прежний `MASTER_KEY`, если ключ LLM уже сохранён в БД).
3. Измените в `.env` только 3 строки:
   ```dotenv
   APP_MODE=public
   PUBLIC_DOMAIN=ваш-домен.ru
   APP_URL=https://ваш-домен.ru
   ```
4. Запустите:
   ```bash
   docker compose --profile public up -d --build
   ```

## 9. Шаг 8. Диагностика и решение типовых проблем

1. **Стек `kotlin` неактивен при создании проекта**:
   На хосте или в WSL2 доступно меньше **3 ГБ ОЗУ**. Увеличьте `memory=6GB` в `.wslconfig` (для Windows) и выполните `wsl --shutdown`.
2. **Ошибка подключения к LLM-шлюзу (`401`, `403`, `502` или таймаут)**:
   Проверьте, что `LLM_BASE_URL` заканчивается на `/v1` (если того требует провайдер), ключ действителен и модели указаны точно как в ответе `/v1/models`. Используйте кнопку **«Проверить»** в «Настройках».
3. **Проект после перезапуска перешёл в статус «Пауза»**:
   Это штатная защита целостности пайплайна при перезапуске процесса. Откройте проект и нажмите **«Продолжить»**.
4. **Остановка с причиной «повторение одинаковой ошибки 2 раза»**:
   Пайплайн автоматически останавливается при двукратном совпадении хэша ошибки и набора файлов, чтобы не тратить бюджет впустую. Проверьте вкладку **«Ошибки стека»** или скачайте логи через **«Скачать логи»**, затем запустите **«Доработать»** с уточнением.
5. **Очистка и повторный прогрев кэшей Docker-раннера**:
   При первом запуске `npm`, `pip` и `gradle` сохраняют пакеты в volumes `npm-cache`, `pip-cache`, `gradle-cache`, а последующие сборки Kotlin используют `--offline`. Если зависимости не меняются (хэш манифеста совпадает), этап `INSTALL` пропускается автоматически.
